## 1. Why the old plan was rewritten

The old plan listed "study the diff with `psx_mts_net`" as a future step but never used what that project and a second one had published, and it predates our REA/Ghidra pipeline. Checked against both, its main claims do not hold:

| Old claim | Verdict now | Evidence |
|---|---|---|
| "The PHY lives in a power domain switched on by Sony firmware before the kernel; nothing a Linux driver can do" | **Withdrawn.** Two other projects bring the link up from Linux after a kexec from Orbis, as we do. Our own log shows the MAC arriving configured and stopped by Orbis, not powered off | [P] 2.1, [V] 2.3 |
| "TX completes and RX does not" | **Neither is hardware evidence.** Our TX reclaim counts a descriptor as finished when bit 31 is clear, which is the value we write when submitting it (D9). Our RX ring is handed to the hardware with the wrong ownership bit, so the hardware never owns it (D8) | [V] 2.4 |
| "Clause 45 always returns 0x0000: the PHY is mute" | **Not evidence of a dead PHY.** Those reads go to MMD 1 and MMD 3 (D7). The firmware's PHY accesses use Clause 22 and MMD 30/31. Our Clause 45 *read* encoding is correct, so the zeros are real reads of registers that read as zero | [V] 2.2, 2.4 |
| "Clause 22 gives a clean echo `0x1000`, so the bus answers but the PHY has no data" (2026-07-30) | **Probably a real PHY read.** We write BMCR `0x1200` and read back `0x1000`: bit 9 (restart autonegotiation) cleared itself, which an echo would not do | [V] 2.3, [I] |
| "PHY ID Marvell `0x888103a2` was bus residue" (2026-07-25) | Possibly wrong: it contains `0x03a2`, the PHYID1 of the MediaTek PHY both other projects read (`0x03a2 9441`). Re-measure | [P]/[U] |
| "MSI and IMR unmasked, `irq_count=0`, so interrupts are not the problem" | **Invalid test.** The IMR polarity used (`0x7d` "unmasked") is inverted: in the firmware a set bit masks (D10). [I] Also, if the driver of that day reset the block as the current code does (D6), the MAC was disabled anyway | [V] 2.2, 2.3 |
| "ICC 4/0x38 only queries status" | Contradicts `AGENTS.md`; on 2026-11-12 the call answered `0x01` on the first try. Not the blocker either way: the MAC block was already configured before the call | [V] 2.3 |
| Step 1 of the old plan: "sweep all of BAR0, read the glue BAR2/BAR4 in documented regions" | **Dropped.** A full BAR0 sweep reads the clear-on-read counters; the glue reads are not needed to answer anything in this plan; sequential glue BAR2 reads are recorded as `HIGH_RISK_POWER_OFF` (`others/rea/acpi/hpet_wdt/HANDOFF.md`) | - |
| Step 3: "decompile `gbe_phy_ctrl` and other glue routines" | `gbe_phy_ctrl` was decompiled on 2026-07-30 but read wrongly (it polls Clause 22 BMSR, not a Clause 45 register; D4). Re-read on 2026-11-17 | [V] 2.2 |

## 2. Evidence

### 2.1 Prior art: two independent, working Baikal Ethernet drivers [P]

| Project | Console / kernel | Result | Driver |
|---|---|---|---|
| [Gcsman110/ps4-mts-linux-driver](https://github.com/Gcsman110/ps4-mts-linux-driver) (Gabriel Stewart) | PS4 Slim CUH-2xxx (Baikal), `ps4-linux` 5.4.247 | About 850 Mbit/s by the driver's own counters. Spec-driven reimplementation with a published register map and a corrections log | `driver/ps4_gbe.c`, GPL-2.0-only; spec `docs/baikal-gbe-register-map.md` |
| [meerzulee/linux-psx](https://github.com/meerzulee/linux-psx) | "one Baikal B1 console" (model not stated), kernels 6.18.44 and 7.2.11 | DHCP, SSH, hash-checked 4 MiB transfers each way, HTTPS; polled mode (1 ms timer); IRQ mode not qualified | `psx_mts_net` (`psx0`), GPL-2.0-only; `docs/ETHERNET.md`, `platforms/ps4/docs/ETHERNET-HISTORY.md` |

What they report:

- **The shutdown residue** (both). Orbis's GBE shutdown writes `0x0010` to Clause 45 register `0x0147`, devad `0x1e` (MMD 30), as its last PHY access. A power cycle clears it; a kexec does not. Gcsman, attempt 29 (control): `0x0147.1e = 0x0010` on arrival, `reg04 = 0x00000b18`, no packet sent in the whole boot. Attempt 30: bit 4 cleared, then the first transmit in thirty boots, with `reg04` bit 0 and BMSR bit 2 set and held for 362 s ("bit4 inhibits the transmit path and holds both link-status bits down"). linux-psx, EXP012: `MMD30:0147 0010 -> 0000`, BMSR `7969 -> 796d`, `BAR0+04 b18 -> b19`, done with the MAC stopped and masked, before any DMA was published.
- **Where to clear it** (Gcsman spec §7.1): one read-modify-write that clears bit 4, before the calibration step of the cold init; "the PHY's register space survives intact" across a kexec.
- **The PHY** is a MediaTek MT7531-family GPHY, PHY ID `0x03a2 9441`, BMCR `0x1040` (both).
- **No cable at launch** (linux-psx EXP-20261017-020): the driver came up without link and the link appeared when the cable was plugged later.
- **TX ring** (Gcsman): the transmitter stops for good after 255 packets on the last descriptor of the 4 KiB ring page; using 255 of the 256 descriptors avoids it. Cause not known.
- **Doorbell** (Gcsman): `0x3c`/`0x40` are the TX/RX *current* pointers; the transmit doorbell is bit 2 of `0x34` ("poll demand"), which reads back as bit 3.
- **IMR** (Gcsman): in `0x54` a set bit masks its source; the operating mask is `0x1018`.

Caveats: Gcsman's console is a Slim and linux-psx does not name the model; **ours is a PS4 Pro with Baikal**, which neither tested. Neither claims long-term stability.

What this shows:

1. The MAC block arrives **configured by Orbis and stopped**, not powered off or reset [V]. This contradicts the 2026-07-24 note in `AGENTS.md` ("`0x04` STABLE_ZERO before the ICC power-on").
2. Orbis's stop ran before the kexec (IMR `0x7ffffa`) [V]. On every firmware path the stop is followed by the residue write (F6, F8), so **the residue was very likely set** [I]. Phase A measures it.

What our driver then did in that boot (all [V] from the same log):

3. MMD 1 and MMD 3 reads all returned `0x0000` in about 43 us each (completed transactions), and the driver concluded "no valid read" (D7).
4. It wrote `1` to both `0x34` and `0x38` (`mts.c:1463-1464`): `0x34` read back `1`, `0x38` read back `0` [U].
5. ICC 4/0x38 answered `0x01` on the first try (the `AGENTS.md` note says a retry loop is required).
6. It asserted the GBE block hold/pulse (glue `0x180020`/`0x180074`). Afterwards `0x04`, `0x08`, `0x0c`, `0x10` read `0`: [I] the block was held in reset (D6). The hold register read back `1`, against the `AGENTS.md` note "hold registers are write-only and read 0".
7. It ran the PHY calibration through the misdecoded packed addresses (D2) and the wrong write opcode (D1).
8. It wrote BMCR = `0x1200` and read back `0x1000` (twice, 21 s apart): the self-clearing restart bit went to 0. [I] A live PHY answered on Clause 22 (one boot, one register).
9. It waited 20 s for link on MMD 1 register 0 (D4): 201 reads of `0x0000`.
10. It ended with `0x34 = 0x38 = 0` and IMR `0`, and registered `eth0` on a reset, disabled MAC (D6).

Older tests, re-read (`test_history`; notes added on 2026-11-17):

- **#61 (2026-07-25)** read BMCR `0x1040` after writing `0x1200`. That is the BMCR value both other projects read from this PHY [P], and it cannot come from our own write. **#62** read "PHY ID" `0x8881`/`0x03a2`; `0x03a2` is the real PHYID1, here in the register-3 slot, which fits each read returning the previous transaction's data. Both were dismissed by **#70** as bus residue, but #70 ran with the Clause 22 wait bug that returned before the transaction finished (fixed on 2026-07-29, `mts.c:277-295`), so it does not refute them. [I] The PHY was answering in July too, read with a broken wait.
- **#50 and #72** ("IMR `0x7d` unmasked, no interrupt"): with 1 = masked, `0x7d` masks bits 0 and 2-6, RX completion included [P]. Invalid tests.

## 5. Prohibitions (any of these = STOP and tell the user)

1. No sequential or block reads of the glue BAR2 (`0xc8800000`), no glue BAR2 writes, no ICC minor sweeps with data=1 (`AGENTS.md`).
2. Do not read the clear-on-read counters (`0x100`-`0x12c`) in "read-only" probes: reading changes them.
3. No `rmmod`/`insmod` of a driver instance after it enabled the MAC or published DMA rings ([P] linux-psx: "a stop acknowledgement is not a DMA-drain proof"). Every experiment that enables the MAC starts from a cold boot.
4. No write that is not in a firmware sequence verified in section 2.2 or added to it in Phase S.
5. One change per boot. Record before/after values.
6. Never test the wired path over the WiFi subnet.

### Phase B - clear the residue (console, one PHY write)
Same boot as Phase A (after the reads) or a fresh one: `insmod mts_peek.ko clear_residue=1`. ### Phase C - data path, polled mode first (console, needs a driver)
Only after Phase B shows link, and after decision E4. Whichever driver: the residue clear (D3), the verified MDIO encodings (D1, D2), the right link poll and BMCR handling (D4, D5), no block reset (D6), RX handed over with bit 31 clear (D8, F15), TX completion on bit 31 set with word2 not idle, and word2 = 0 on submit (D9, F10, F14), IMR with 1 = masked and `0x1018` as the operating value (D10, F17), the doorbell `0x34 |= 4` once per batch (D11, F13), 255 TX descriptors (D12), no `BAR0+0x1c8` write in the stop (D13). Start in polled mode (linux-psx polls at 1 ms), on the inherited baseline: no cold init, no calibration, no hold/pulse. The polled loop copies what the interrupt handler does (F20): read `0x50` and write it back, reclaim TX, ring the TX doorbell again if descriptors are still outstanding, drain RX, ring the RX doorbell `0x38 \|= 4` when `status & 0x22` (and after a drain that handled frames, as a harmless superset), log the error bits, and do not unmask the interrupt line.

**Rule for the code.** `mts` loads on every boot today (D14). A change to `kernel/drivers_mts/mts.c` that alters what it writes would reach every boot of the console as soon as a build picks it up. So the corrected driver is a **separate module**, `others/tools/mtsx/` (no `MODULE_DEVICE_TABLE`, loaded only by an explicit `insmod`, `mts.c` untouched). If E4 goes the other way (fix `mts.c`), the changes go in behind a module parameter (`fw_bringup`, default 0) and the default stays the legacy path until three cold boots pass; only then it flips.

**Vehicle for this phase: `others/tools/mtsx/`** (README there). It implements every item of the list above on the inherited baseline, polled, and was checked on the host: it compiles with `W=1` without warnings, `checkpatch --strict` is clean, and `test_desc.c` pins the descriptor bit patterns to the firmware's values and runs a model of the ownership protocol over 255, 256 and 192 TX descriptors and the RX ring (including the full-ring path). The model is our reading of the firmware, so it checks the driver's bookkeeping, not the hardware. Open points that only the console can settle are listed in its README (FCS in the RX length, short-frame padding, 255 versus 256, the meaning of the completion status bits, `ip link` down/up, the PS4 Pro itself). Tests on `192.168.0.0/24`: ARP and ping both ways, then hash-checked transfers both ways (`sha256sum` at both ends), counters (`ip -s link`), UART capture during the boot. Acceptance: three cold boots with verified transfers, then a 30-minute transfer, then Orbis networking still healthy afterwards (the user checks).

## 8. The experiment loop

- With `module_blacklist=mts`, nothing in Linux touches the GBE; the hardware state is the one Orbis left.
- Diagnostic modules are built on the host, copied with `scp` to `/dev/shm` (RAM) and loaded once per boot. The USB root drive has known I/O errors, so nothing is written to it during experiments.
- A boot that enabled the MAC (Phase C) is never reused: power off, cold boot into Orbis, payload, next experiment.
- Boot files are switched over FTP (`distro/deploy-boot-ftp-7.0.sh <TAG>` in Orbis mode); the rootfs stays on the USB drive.
