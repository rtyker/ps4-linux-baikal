## Estado atual do kernel Linux para GbE

**O que o Linux faz por outros dispositivos (funciona):**
- Wi-Fi: `bpcie_icc_cmd(5, 0, &on=3, ...)` → liga via ICC
- USB: `bpcie_icc_cmd(5, 0x10, &on=1, ...)` → liga via ICC
- SATA/xHCI: `bpcie_baikal_sata_phy_init()` → hold/pulse + calibra\u00e7\u00e3o PHY

**O que o Linux N\u00c3O faz para a GbE:**
- Nenhuma chamada ICC equivalente
- Nenhuma `bpcie_baikal_gbe_release()` ou equivalente
- O `sky2.c` patched s\u00f3 cuida de: PCI ID, IRQ routing, fix BAR0 4KB

## Pr\u00f3ximo candidato concreto: `Major 5, Minor 0, Payload 0x07`

### Fundamenta\u00e7\u00e3o (do `ICC_GBE_TEST_LOG.md` se\u00e7\u00e3o 2 dos Testes de 2026-07-21)

O payload de kexec envia `kern.wlanbt(0x2)` → ICC `Major 5, Minor 0, Payload 02`.  
O driver Linux reenvia `bpcie_icc_cmd(5, 0, &on=3, ...)` → Payload `03` (bits 0+1 = WLAN+BT).

**Teoria:** A GbE pertence ao mesmo dom\u00ednio `Major 5, Minor 0`, controlada pelo **bit 2** (valor `0x04`). Logo:
- `0x03` = WLAN + BT (o que o Linux faz hoje)
- `0x07` = WLAN + BT + **GbE** (o que precisamos)

**Por que n\u00e3o foi testado ainda:** o teste anterior com `5 0 02` derrubou o Wi-Fi e cortou o Telnet antes de chegar no `07`. O teste correto usa **payloads seguros** que mant\u00eam os bits 0+1 ligados: `03`, **`07`**, `0B`, `0F`.

### Precau\u00e7\u00f5es obrigat\u00f3rias (da LICOES_APRENDIDAS.md):
> **NUNCA** testar payloads `Major 5, Minor 0` que n\u00e3o tenham os bits 0 e 1 ativados.  
> Qualquer valor sem bit 0+1 (`03`, `07`, `0B`, `0F`) **derruba Wi-Fi e mata o Telnet**.

## Plano de Testes

### Fase 1 — Teste seguro: `Major 5, Minor 0, Payload 0x07` via `/proc/ps4_icc`

**Ambiente:** Sistema bootado na tag `20260720-sky2len-fix`, Telnet ativo em `192.168.6.128`.

**Script `test_safe_bitmasks.py` (j\u00e1 mencionado no ICC_GBE_TEST_LOG.md):**
```python
#!/usr/bin/env python3
# Testa somente payloads seguros (bits 0+1 sempre ligados)
safe_payloads = [0x07, 0x0B, 0x0F]  # 03 ja est\u00e1 ativo (estado atual)
for payload in safe_payloads:
    cmd = f"5 0 {payload:02x}"
    # Ler ChipID antes
    baseline = read_chip_id()   # dd from 0xc2000118
    # Enviar ICC
    send_icc(cmd)              # echo cmd > /proc/ps4_icc; cat /proc/ps4_icc
    # Ler ChipID depois
    result = read_chip_id()
    print(f"Payload {payload:#04x}: ChipID {baseline} -> {result}")
    if result != '00 00 00 00':
        print("SUCCESS: GbE respondeu!")
        break
```

**Ordem:** `0x07` primeiro. Se ChipID mudar de `00 00`, rebind `sky2`:
```bash
echo -n "0000:00:14.1" > /sys/bus/pci/drivers/sky2/bind
dmesg | tail -20
```

### Fase 2 — Se `0x07` funcionar: tornar permanente no `ps4-bpcie-icc.c`

## Regras de Seguran\u00e7a para Todos os Testes

> [!CAUTION]
> **Um teste por power cycle.** N\u00e3o reinjetar sem reiniciar completamente (tirar da tomada 15-30s).

> [!WARNING]
> **NUNCA** testar ICC `Major 5, Minor 0` com payload que n\u00e3o inclua bits 0+1: `01`, `02`, `04`, `05`, `06` derrubam Wi-Fi e matam o Telnet.

> [!WARNING]
> **NUNCA** colocar leituras de BAR2 `0x180000+offset` dentro de fun\u00e7\u00f5es do caminho de boot do kernel (repeat do M7). Leituras de novos registradores da glue = primeiro via `/dev/mem` userspace, um por vez.

> [!CAUTION]
> **NUNCA** escrever em `0xc890a030` durante o boot (`bpcie_glue_init`) — causa tela preta (M4).

> [!NOTE]
> **Telnet, n\u00e3o SSH** para testes. Sempre confirmar `DEBUG LOOP` na TV continua subindo entre comandos — \u00e9 o desempatador entre DEAUTH de WiFi e travamento real.
