### 2.1 `rtc_mvl_probe` @ `0xffffffffdc5d63f0` (89 B)

```c
ulong rtc_mvl_probe(int64_t dev)
{
    int64_t res;
    ulong   rv = 0;

    res = func_0xffffffffdc5661b0();        // bus_alloc_resource_any / rman_get_resource
    *(dev + 0x28) = res;                    // softc->ri_rid = res  (guarda resource)
    if (res == 0) {
        // device_printf(dev, "%s: cannnot allocate resource", "rtc_mvl_attach");
        func_0xffffffffdc630420("%s: cannnot allocate resource", "rtc_mvl_attach");
        rv = 6;                              // ENXIO
    } else {
        // device_set_desc(dev+8, "rtc_mvl", 0, 0);
        func_0xffffffffdc6c8d70(dev + 8, "rtc_mvl", 0, 0);
    }
    return rv;                               // 0 = OK, 6 = ENXIO
}
```

Prólogo padrão FreeBSD (`push rbp; mov rbp,rsp; push r14; push rbx`).
A função `0xffffffffdc5661b0` é o allocator de resource — também chamada por outros
drivers Baikal com o mesmo padrão. O nome "rtc_mvl_attach" hard-coded na mensagem de
erro é apenas o `__func__` do caller em printf logs.

### 2.2 `rtc_mvl_attach` @ `0xffffffffdc5d6450` (427 B)

```c
ulong rtc_mvl_attach(int64_t dev)
{
    uint32_t *base  = *(*(dev + 0x28) + 0x10);   // softc->res.bsh (bus_space handle)
    uint32_t *stat  = base + 0x100;              // status register
    int       is_mmio = *(*(dev + 0x28) + 8);    // bus_space_tag flag (0 = port I/O)

    uint32_t s = is_mmio ? *stat          : in(stat);    // read STATUS
    uint32_t status_extra, time_extra;
    char    *fmt;

    if ((s & 0x100) != 0) {                       // bit 8: Battery failure indication
        if ((s & 0x4) != 0)  return 0;            // bit 2: tudo OK → sai silencioso
        // WARNING: Clock failure indication
        device_printf(*dev, "WARNING: Clock failure indication");
        fmt = "[Bug 142260] Status:%X, Time:%X";
    } else {
        // WARNING: Battery failure indication
        device_printf(*dev, "WARNING: Battery failure indication");
        fmt = "Status:%X, Time:%X";
    }
    // Lê 4 registradores sequenciais do "time+status" : 0x130,0x134,0x138,0x13c
    uint32_t t0 = R(base, 0x130);
    uint32_t t1 = R(base, 0x134);
    uint32_t t2 = R(base, 0x138);
    uint32_t t3 = R(base, 0x13c);      // último = STATUS extra / Time༣ high
    // device_printf(*dev, fmt, s, t3);
    device_printf(*dev, fmt, s, t3);
    return 0x16;                       // 22 = EINVAL (attach falhou, dispositivo não saudável)
}
```

Onde `R(base, off)` lê com `in()` se `is_mmio==0` ou `*(base+off)` se MMIO.

**Registradores do RTC Aeolia/Marvell** (BAR/mapping em `softc+0x28+0x10`):

| offset | leitura | papel |
|---|---|---|
| `0x100` | STATUS | bit 2 = OK; bit 8 = "battery failure indication" (clock OK mas sem bateria) |
| `0x130` | TIME[0] | byte 0 do timestamp (LSB) — lido por `read_aeolia_rtc` para retry |
| `0x134` | TIME[1] | byte 1 |
| `0x138` | TIME[2] | byte 2 |
| `0x13c` | TIME[3] | byte 3 (MSB) — também exibido no log "Time:%X" |
| `0x160` | extra  | lido em `rtc_mvl_gettime` |
| `0x164` | extra  | lido em `rtc_mvl_gettime` |

Padrão `Bug 142260` é um número de bug interno da Sony — aparece em 14 outras funções do kernel
(swiotlb, gpu, idle, etc.); parece denotar workaround de silicon.

### 2.3 `read_aeolia_rtc` (básica) @ `0xffffffffdc5d6600` (619 B)

```c
ulong read_aeolia_rtc(int64_t dev, uint32_t *out)
{
    mtx_lock_or_assert(dev+8, "rtc_mvl.c", 0x6d);   // func_0xffffffffdc6c8300
    uint32_t v0 = R4(base, 0x130,0x134,0x138,0x13c);   // primeiro snapshot (32-bit BE)

    uint32_t prev = v0;
    uint32_t i = 1;
    for (;;) {
        func_0xffffffffdc4afb10(100);     // DELAY(100) microseconds
        uint32_t cur = R4(base, 0x130,0x134,0x138,0x13c);

        if (prev == cur) {                 // leitura estável
            *out = cur;
            mtx_unlock(dev+8, "rtc_mvl.c", 0x95);
            return 0;
        }
        if ((i % 10) == 1) {               // logaritmic logging
            device_printf("read_aeolia_rtc: retry %d times. %08x != %08x", i, cur, cur);
            // (BUG na decompilação: ambos args 4 = cur; na verdade são prev != cur)
        }
        i++;
        prev = cur;
    }
}
```

`R4` é a montagem de 4 reads `in()` / `*(p)` concatenados (low→high):
`v = t3<<24 | t2<<16 | t1<<8 | t0`. Note que o `0x13c` é o **MSB** (shift `<<0x18`).

Loop clássico de "leitura viajando" — protege contra o caso de o timestamp
mudar exatamente durante a leitura dos 4 bytes, re-le até duas leituras consecutivas baterem.
DELAY 100 us entre tentativas. Logging de progressão logarítmica (i%10==1).

### 2.4 `rtc_mvl_gettime` @ `0xffffffffdc5d6870` (644 B)

```c
ulong rtc_mvl_gettime(int64_t dev, struct timespec *ts /* arg2 */)
{
    uint32_t s   = R(base, 0x100);   // STATUS primeiro snapshot
    ts->sec   = s;                   // !? guardou status em sec? (provavelmente nome simbólico confuso)

    mtx_lock_or_assert(dev+8, "rtc_mvl.c", 0xa1);

    uint32_t prev = R4(base, 0x130,0x134,0x138,0x13c);   // primeira leitura 32-bit BE
    uint32_t i = 1;
    for (;;) {
        DELAY(100);  // func_0xffffffffdc4afb10(100)
        uint32_t cur = R4(base, 0x130,0x134,0x138,0x13c);

        if (prev == cur) break;

        if ((i % 10) == 1)
            device_printf("[Bug 55086] read_aeolia_rtc: retry %d times. %08x != %08x", i, cur, cur);
            // (mesma BUG na decompilação mostrada — provavelmente prev,cur)

        i++;
        prev = cur;
        if (i == 0x15) {                      // 21 tentativas
            device_printf("[Bug 55086] retry error, timeout");
            break;
        }
    }
    ts->sec = prev;                            // offset 4

    mtx_unlock(dev+8, "rtc_mvl.c", 0xce);

    ts->nsec = R(base, 0x160);                 // offset 8  — campo "extra" 0x160
    ts->pad  = R(base, 0x164);                 // offset 12 — campo "extra" 0x164

    return 0;
}
```

Diferencia de `read_aeolia_rtc` (2.3) por:
- Também ler **STATUS** primeiro e armazenar em offset 0 do output (`ts->status_provavel`).
- Ser chamada pelo `clock_gettime` do kernel — tem **timeout** máximo (21 tentativas × 100 us = 2.1 ms).
- Após a leitura estável, ainda lê `0x160` e `0x164` — provavelmente **sub-segundos / tick counter**.
- Usa strings "Bug 55086" (mantém identidade histórica de bug).
- `mtx_lock_or_assert` aparece DUAS vezes: linha 0xa1 e 0xce — i.e. `mtx_lock` + `mtx_unlock`.

## 3. Diagrama do softc (deduzido)

```
struct rtc_mvl_softc {
    ...
    void    *ri_dev;            // +0x00   dev_t
    void    *ri_label;          // +0x08   "rtc_mvl"
    void    *ri_pad;            // +0x10..0x27
    struct resource *ri_res;    // +0x28   bus_alloc_resource
        // resource: +0x08 bus_space_tag, +0x10 bus_space_handle
    ...
};
```

`softc->ri_res` é a estrutura FreeBSD `struct resource`. Campos conhecidos:
- `+0x08` = `r_bustag` (não-zero se MMIO, zero se port I/O)
- `+0x10` = `r_bushandle` (ponteiro/base do mapping)

O teste `if (*(softc+0x28)+0x08 == 0)` desambigua between `in()` e `*(p)` — ou seja o
 driver é compatível com port I/O **e** MMIO; o Baikal usa MMIO.

## 5. Lacunas / pendências

| Função | Origem da referência | Estado |
|---|---|---|
| `0xffffffffdc5d6600` revisita | —— | revisado neste arquivo (assume read básica) |
| `0xffffffffdc5d660b` dentro de read_aeolia_rtc | sub-rotina | pode ser inline |
| `settime` (`rtc_settime`) | ausente neste cluster | possível função fora do range 0x2863?? — não há strings `settime`/`write_aeolia_rtc` no módulo, sugerindo que este driver **não implementa escrita no RTC** (somente read + gettime) |
| detach | ausente | sem string `_detach` — driver sem detach explícito (sempre attach-only) |

Implicação importante: o RTC Aeolia Marvell do PS4 é **read-only** no driver FreeBSD
Orbis — nenhuma função de settime ou write foi localizada nas strings do módulo.
Isso é consistente com o `BOOTARGS.md` do projeto Linux, que injeta tempo via `time=`
cmdline em vez de escrever no hardware.
