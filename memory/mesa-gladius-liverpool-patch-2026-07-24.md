Ambiente desktop (Xorg + Cinnamon) instalado no PS4 (a pedido do usuário, "só um teste pessoal") apresentou corrupção visual real em janelas compostas via OpenGL (padrão xadrez azul/branco). Mitigação imediata `AMD_DEBUG=notiling` (em `/etc/environment` do PS4) elimina o sintoma mas custa performance.

**Causa raiz confirmada por leitura de código-fonte** (não é só teoria): o kernel deste projeto já tem `CHIP_GLADIUS` (PS4 Pro, PCI `0x9924`) e `CHIP_LIVERPOOL` (PS4 base) implementados em `drivers/gpu/drm/amd/amdgpu/`, com valores reais de hardware (`gfx_v7_0.c`) e `external_rev_id` calculado especificamente para integração com Mesa (`cik.c`, `rev_id + 0x61`/`+0x71`). Mas o Mesa binário instalado (pacote oficial Arch, sem patch) não reconhece esses chips — recebe do kernel a família genérica `AMDGPU_FAMILY_KV` e usa o `raster_config` da Kaveri (1 SE/2 RBs) num hardware de 4 SEs (PS4 Pro), gerando o descasamento que corrompe a tela.

Esse problema já foi resolvido publicamente pela comunidade PS4-Linux desde 2017 (fail0verflow) e mantido por forks (Ps3itaTeam, paranoidnela). Os 3 patches de referência foram baixados e comparados; um patch equivalente foi escrito para Mesa 26.1.5 (versão atual do projeto), tocando 5 arquivos (`radeonsi_pci_ids.h`, `amdgpu_asic_addr.h`, `amd_family.h/.c`, `ac_gpu_info.c` — este último com o fix mais importante, `ac_get_raster_config()`).

**Por quê isso importa:** confirma que a arquitetura de kernel deste projeto (drivers `CHIP_GLADIUS`/`CHIP_LIVERPOOL`) foi desenhada desde o início para ser usada com um Mesa patched — não é um acaso que os valores de `external_rev_id` batem exatamente com as faixas que os patches de Mesa esperam. Só faltava a metade userspace.

**Como aplicar:** ver documento completo em `consolidado/MESA_GLADIUS_LIVERPOOL_FIX.md` (investigação, patch, comando de build, resultado do teste ao vivo). Patch pronto em `mesa/ps4-gladius-liverpool-patch/mesa-26.1.5-ps4-gladius-liverpool.patch` (inclui fix de um bug de build separado em `radeon_surface.c`, enum privado do driver clássico `radeon.ko` nunca usado no PS4 mas que precisa compilar). Script canônico de build em `mesa/01-build-mesa.sh` (baixa versão compatível ou `--latest`, aplica patch, compila, empacota).

**✅ VALIDADO AO VIVO 2026-07-24:** build nativo no host (mesma glibc/libdrm/mesa do PS4) deployado em `/opt/mesa-ps4-patched/` no console via `LD_LIBRARY_PATH=/opt/mesa-ps4-patched/lib` + `LIBGL_DRIVERS_PATH=/opt/mesa-ps4-patched/lib/dri` (as duas variáveis são necessárias — só `LIBGL_DRIVERS_PATH` não bastou, o loader ainda abria o `libgallium` do sistema). `glxinfo` passou a mostrar `gladius` em vez de `kaveri`, e a corrupção visual sumiu completamente mesmo sem `AMD_DEBUG=notiling`. Confirmado visualmente pelo usuário na TV do console, não só por mim.

**✅ Persistente e integrado ao pipeline (2026-07-24):** `mesa/01-build-mesa.sh` agora produz `mesa/mesa-ps4-gladius-liverpool-latest.tar.xz` (cópia estável, não versionada); `distros/arch_minimal_v2/01-build-image-7.0.sh` extrai esse tarball pra `/opt/mesa-ps4-patched` dentro do rootfs e persiste `LD_LIBRARY_PATH`/`LIBGL_DRIVERS_PATH` em `/etc/environment` (mesmo mecanismo validado ao vivo, via `pam_env`). Passo é opcional/best-effort (não falha o build da imagem se o tarball do Mesa ainda não tiver sido gerado), igual ao tratamento já existente pro `mts.ko`. Não sobrescreve os arquivos do pacote `mesa` oficial do Arch (que já estava em `IgnorePkg` do `pacman.conf` do rootfs) — só empilha por cima via env var, evitando conflito com `pacman -Syu` e com os sufixos de versão (`-archX.Y`) que mudam a cada rebuild do pacote oficial. **Ainda não testado:** rodar o `01-build-image-7.0.sh` completo com esse passo novo e gravar a imagem do zero num power cycle real (só foi validado o equivalente manual, num sistema já rodando). Um Mesa customizado de terceiros (`mesa/custom-mesa-arch-v1-ps4linux.tar.xz`) foi tentado antes e descartado por incompatibilidade de ABI (LLVM 9 + libxml2 antigo).
